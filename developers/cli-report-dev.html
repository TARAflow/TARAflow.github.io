CLI Report Generator

taraflow-report — a headless entry point that generates the exact same documentation as the Documentation tab, from a saved .tara.json file, with no UI and no Electron. Built for CI/CD pipelines and containers where launching the desktop app isn't practical.

01

Entry-point separation, not a runtime switch

  • Two independent entry points share only the pure generation core: main.tsx (Electron/browser renderer) and bin/taraflow-report.ts (plain Node) — there is no branch in main.tsx/app.tsx that decides "am I headless?"
  • The purity boundary (invariant): no module in the generation path (features/documentation/{models,utils}/**) may import a feature barrel (features/*/index.ts), react, react-dom, @mui/*, draw.io, or any module with a top-level window/document reference. import type edges are exempt — they're erased at build time and carry no runtime weight
  • The boundary is enforced with a dependency-cruiser rule (tools/depcruise-doc.cjs), introduced as a warning first and promoted to a CI-failing error once the existing barrel imports are cleaned up
  • The renderer's own PDF path (pdf-generator-renderer.ts, window/IPC-based) and the UI's doc-generator.ts factory are never touched — the CLI gets its own factory (cli-generators.ts) that imports the four pure generators directly, never through the barrel that would drag in the renderer's PDF module
02

What changes vs. what's additive

  • Exactly one category of change touches existing files: swapping barrel imports for deep-path imports in the generation path (e.g. DFD formatters, risk mitigation helpers, threat catalog resolvers, shared tag utilities) — runtime-identical, the renderer resolves the same functions as before
  • Everything else is additive: new files under bin/ (CLI entry, arg parsing) and cli/ (Node-side i18n init, project loader, Project → DocProjectData mapper)
  • The i18n singleton is reused as-is in Node once initialized with a filesystem resource backend instead of the browser's — namespaces actually used by templates/mappers must all be registered, or raw i18n keys leak into the report instead of labels
03

Loading a project outside the app

  • No storage-service dependency (that's Electron/browser-coupled) — a plain fs.readFile + JSON.parse, followed by the same schema migrations the app runs on load (risk data, asset configuration, factor ratings)
  • The project's computed maps (e.g. impactLabels) must be present as empty Maps, never undefined — the base generator accesses them with a nullish-coalescing fallback on the value, not on the map itself
  • attackTree (singular, in DocProjectData) maps from project.attackTrees (plural) — a naming mismatch worth knowing about before it causes a silent empty section
  • The on-disk DFD thumbnail is already a base64 SVG — reports embed it directly, no headless draw.io instance needed
04

Build & packaging

  • Its own tsconfig.cli.json (extends the base config) keeps the renderer's build untouched; path aliases (features/*, shared, i18n) are resolved via tsx + tsconfig-paths, or bundled with esbuild --platform=node using an alias plugin mirroring the same tsconfig paths
  • Distributed as a standalone .deb package (depends only on nodejs), decoupled from the Electron desktop installer — installs taraflow-report straight to /usr/bin
  • PDF output reuses the already-present puppeteer dependency directly in Node (HTML string → Puppeteer → PDF), deliberately not the renderer's Canvas-based PNG path — the DFD thumbnail SVG is embedded in the HTML and rasterized by Puppeteer
05

CI guardrail

  • The dependency-cruiser rule runs as a hard CI failure: any reintroduced barrel/react/draw.io import in the generation path breaks the build immediately, not just a lint warning
  • A smoke test generates a report from a fixture project and asserts the output is non-empty and contains the expected chapter titles
  • The CLI binary itself runs against that fixture as a CI job, not just its library code in isolation
