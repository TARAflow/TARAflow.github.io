Methodology

Asset Relationships & the Knowledge Graph

TARAflow's graph has two connected levels: DFD elements linked by data flows, and assets linked both to those elements and to each other. This page covers how that graph is built, how Hazard Items and Safety Annotation extend it, and the four-phase methodology that uses it.

01

Two levels, one graph

Level 1: DFD elements --(Data Flows)-- DFD elements | element-to-asset relationships (typed) Level 2: Vertical Data Assets --, static structure (abstraction) Function Assets --| (what / with what / where) System Assets --| Infrastructure Assets| |--(asset-to-asset relationships)-- Orthogonal Process Assets --| dynamic context (context) Physical Assets --| (how / with what / who) Service Assets --| Human Assets --| Environment Assets --' protection target (environment) Hazard Hazard Item <--contributes_to-- Assets (not an asset) --endangers--> Human / Environment / Infrastructure

Level 2 is a heterogeneous graph — which relationship types are allowed depends on the combination of source category × target category, the same principle as Level 1 where DFD element types (Process, DataStore, ExternalEntity...) have type-dependent connection rules.

02

Element-to-Asset: the Active-Impact model

Every relationship between a DFD element and an asset follows one pattern: DFD element → acts on → Asset. Two perspectives make the threat analysis complete:

RelationshipFocusTARA relevance
usesInteractionWhere is the attack vector? (Likelihood)
depends_onAvailabilityHow severe is the damage on failure? (Impact)
  • uses (with qualifiers) — how could an attacker compromise the system through this element?
  • depends_on — what cascading effects occur if this asset becomes unavailable?
03

is_an — the exclusive, definitional relation

  • A DFD element is either an instance of the asset (is_an) or it has impact relationships to the same asset — never both, to the same asset. Relationships to other assets remain unrestricted.
  • Formally: is_an(A, X) ⇒ no further relationships between A and X are allowed.
  • Not transitively inherited itself: is_an(A, X) does not inherit X's own relationships onto A.
  • Mathematically, is_an creates a logically unambiguous bridge used for transitive derivation elsewhere in the graph (see Phase 2 below).

Example: External Entity "Administrator" is_an Human Asset "System Admin Role" (no further relations to this asset allowed). Process "User Management" creates Data Asset "Admin Audit Logs" (not is_an — it's a byproduct of logging admin actions). Data Asset "Admin Audit Logs" then affects_privacy Human Asset "System Admin Role".

04

Asset categories & abstraction hierarchy

Four vertical categories form a static abstraction hierarchy — the higher the level, the less implementation detail is known or needed.

Infrastructure <- highest level, least precision (environment / arena) | houses System <- blackbox component (what does the Function provide?) | realizes Function <- capability (what must the system be able to do?) | relies on Data <- lowest level, highest precision (atomic values)

Where an analyst enters the hierarchy determines their perspective — a product developer thinks in Function/Data, an integrator in System, an operator/CISO in Infrastructure. Same method, different scope.

Four orthogonal categories cut across every vertical level instead of sitting inside the hierarchy:

Process

Orchestrator

Temporal sequence of steps, a know-how asset — a manufacturing recipe, a GMP production instruction, a treatment protocol.

Physical

Passive value

A material asset with no embedded system — valuables, a museum painting, a prototype, a physical key.

Service

External/internal

A service outside the system's own boundary — a cloud service, an OTA update server, external maintenance.

Human

Protection subject & actor

Operator, patient, administrator — both something to protect and someone who acts.

05

Function vs. Process

These two are frequently confused. Three questions decide it:

1. Do you know the temporal order of the steps? No -> Function 2. Is the asset's value in the runtime sequence? (would a sequencing attack or race condition be a relevant threat?) No -> Function 3. Is the flow instantiated at runtime? (is there a concrete "running instance" that can be started/stopped?) No -> Function Yes -> Process

Edge case: even simple, linear flows with no security-relevant sequencing are Process assets if they exist as a runtime instance (e.g. cronjobs, batch processes) — question 3 is what decides it.

06

Asset-to-Asset: a two-tier ruleset

Asset-to-asset relationships describe causality that exists independently of the data flow — safety, privacy and physical dependencies between assets that don't naturally express themselves through a DFD element.

  • Core Rules — generic, domain-independent, built into the tool, analytically active (feeds STRIDE, Safety, criticality)
  • Domain Extensions — domain-specific, configurable in the project profile or defined manually; documentary by default, optionally analytically active with a mandatory rationale

Completeness is the goal of the rulebook, not of every model — a handful of core relationships cover most real projects:

RelationshipFrom → ToPurpose
depends_onSystem/Service/Process → *Availability dependency (DoS)
required_byData → Process/FunctionInput dependency (Tampering)
contributes_toAsset → Hazard ItemContribution to a hazard (carries relevance)
endangersHazard Item → Human/Environment/InfrastructureEndangers a protection target (carries impact)
affects_privacyData/Process → HumanPrivacy relevance
configuresData → Function/SystemConfiguration dependency
runs_onProcess → SystemExecution context
implementsSystem/Process → FunctionArchitecture assignment
hosted_onSystem → InfrastructurePhysical embedding

Rule of thumb: depends_on = "if X fails, I fail too." required_by = "I need X as input to function." consumed_by = "X is transformed by me."

07

Hazard Item — the explicit hazard node

A Hazard Item is its own node type, on an orthogonal level alongside Physical, Process, Service, Human and Environment — but it is not an asset. An asset is something worth protecting; a Hazard Item is the hazard itself, the convergence point where one or more hazard-causing assets meet, and from which one or more protection targets are endangered.

Asset --contributes_to [relevance]--> Hazard Item --endangers [impact]--> Protection target
  • contributes_to (Asset → Hazard Item) carries relevance (direct/indirect) — does this asset control or enable the physical action behind the hazard?
  • endangers (Hazard Item → protection target) carries impact — what harm threatens the target?

The endangered target's type derives the impact dimension automatically:

Target nodeDerived dimensionScale / norm
HumanSafetyreversible · irreversible · fatality (ISO 12100)
EnvironmentEnvironmentalminor · moderate · severe (Seveso / environmental liability)
InfrastructureAsset destructionminor · major · critical

combinationType decides how multiple contributing causes combine: ANY (default, OR-gate — a single cause is enough, e.g. over-pressure or over-heating → tank explosion) or ALL (AND-gate, combinatorial — e.g. sodium and water → exothermic reaction). Multiple contributes_to inputs never imply combinatorics automatically; it's always explicit via combinationType.

The Hazard Item always exists in the data model, but isn't always shown: with exactly one derivable input it stays collapsed (the analyst just draws a direct endangers edge, and the tool creates the Hazard Item internally); a second contributes_to input on the same hazard automatically expands it, since the combinatorics need to be visible.

08

Safety Annotation Layer

TARAflow integrates safety aspects through an optional annotation layer that introduces no new modeling logic — it enriches existing relationships with safety context.

  • Optional — only needed for safety-relevant systems
  • Qualitative — explanatory ratings, no complex calculations
  • Non-invasive — doesn't change the core security analysis
  • Norm-compliant — enables EN 50742 / ISO 12100 compliance
safety: { relevance: "none" | "indirect" | "direct"; impact?: "none" | "reversible_injury" | "irreversible_injury" | "fatality"; physicalHazardPotential?: "low" | "medium" | "high"; // ISO 12100 / EN 50742 protectionTarget?: boolean; // specifically for Human Assets rationale?: string; }

This pattern is uniform across every DFD element and asset relationship. It also drives threat prioritization directly:

If (asset.safety.relevance === 'direct' || asset.safety.impact === 'fatality') -> Risk Priority = CRITICAL (independent of business impact) -> Requires additional mitigations -> Explicit documentation in the Safety chapter

What Safety Annotation is not: a replacement for formal safety analysis (FMEA, FTA), an SRSL calculation, an ISO 13849 Performance Level determination, or automatic safety certification. It is a documented bridge between cybersecurity and functional safety, with traceable prioritization of security measures.

09

The methodical chain: Threat → Impact → Injury

Threat -> Impact -> [Hazardous Situation] -> Injury / Harm

The hazardous situation sits conceptually between impact and injury; it's modeled as the Hazard Item above, and in the simplest case (one input, derivable hazard) stays collapsed rather than needing its own explicit field. TARAflow works conservatively: once a threat produces an impact on a safety-relevant asset, the resulting hazardous situation is treated as given — a worst-case assumption.

10

Four phases, one growing graph

1

Foundation & pragmatic modeling

Classic STRIDE threat modeling with tool support. Safety annotation is available but entirely optional and non-invasive. Builds a consistent base graph (DFD + assets + relationships) and a first threat identification — not yet a full automatic derivation.

2

Rule-based completion & derivation

is_an-based derivations activate; relationships are extended transitively where semantically valid (e.g. a Process inherits relationships from a Data Store via is_an). A validation engine flags incomplete nodes, invalid relationship types, and semantically contradictory modeling — every automatic derivation is explained to the user.

3

Deterministic threat derivation

Likelihood-related relationships (uses, transports) and impact-related relationships (depends_on, affects_*) are strictly separated. Full path computation from attack vectors to damage targets, using only explicit and derived relationships — no heuristic assumptions.

4

Analysis support & governance (optional)

Prioritization and filtering of threat paths, traceable documentation of modeling decisions, support for reviews, audits and standards conformance, versioning and comparison of graphs over the system's lifecycle.
