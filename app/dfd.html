App / 03

DFD Modeling

TARAflow uses draw.io as its DFD editor. Import or draw your data-flow diagram, then parametrize each element with type, technology, protocol, and security properties.

01

Element Types

Process [P-xx]

Process

Software component, service, or controller. Context: technology (api, microservice, daemon, ui, cli, rtos_task, bare_metal, isr, bootloader, driver, logic_module …), exposed to Internet. Security in sub-tabs: authentication and accounts, authorization, secure channels, input validation, malware protection, sessions, update mechanism and delivery, secure by default, user data deletion.

Multiprocess [MP-xx]

Multiprocess

A composite of processes — decomposed on a child page (leveled DFD) or kept as a black box with Inside fields for what it contains. Security in sub-tabs like a process, plus boundary authentication.

DataStore [DS-xx]

DataStore

Storage. Properties: technology (database, filesystem, cloud, cache, queue, flash, eeprom, nvram, shared_memory, mmio_register …), stored data and classification, encryption at rest, access control and access model, integrity protection, backup, deletion policy, safety-relevant data.

DataFlow [DF-xx]

DataFlow

Communication channel. Properties: protocol, medium (logical / physical), location (on_chip, on_board, in_enclosure, field_cable, local or enterprise network, wireless, internet, in_process), encryption in transit, integrity protection, endpoint authentication, exposure level, access mode, data minimisation, safety function.

ExternalEntity [EE-xx]

ExternalEntity

Actor outside the system boundary — and the physical environment a sensor measures or an actuator acts on. Properties: entityType (user and admin roles, operator, maintenance, remote service, SCADA / HMI, gateway, controller, engineering workstation, debugger …), trustLevel, authenticationMethod.

TrustBoundary [TB-xx]

TrustBoundary

Logical security zone boundary. Threats are generated at crossing points. Several traffic policies — default deny, island mode, fail close — as IEC 62443 counts them separately.

PhysicalBoundary [PB-xx]

PhysicalBoundary

Physical enclosure boundary. Properties: boundary type, physical exposure level, mobility, accessibility, tamper protection, physical access control, monitoring, debug interface and removable media accessible, tool required for access.

ChipBoundary [CB-xx]

ChipBoundary

Hardware security boundary. Properties: chip type (MCU, SoM, FPGA, secure element, HSM, DSP), debug interface present / locked, secure boot, firmware protection, bitstream encryption, tamper protection, supply-chain trust, authenticator storage, crypto standard.

Sensor [SE-xx]

Sensor

Transducer physical → cyber, only the conversion itself. Physical side: a data flow with medium physical from an ExternalEntity; cyber side: to a Process or Interface. Properties: measurand, transduction principle, stimulus domain, sensing exposure, signal authentication, plausibility check, redundancy, loss detection, safety relevance.

Actuator [AC-xx]

Actuator

Transducer cyber → physical, typically the top event of a hazard. Receives the command from a Process or Interface, acts on an ExternalEntity. Properties: actuator class, energy domain, hazard potential, command authentication, safe state, fail behavior, feedback verification, hardware interlock, safety relevance.

Interface [IF-xx]

Interface / PhysicalInterface

Physical or logical interface port. Properties: type, location, operational state, exposure level, implemented controls (link authentication, physical access protection, debug protection, service access policy, abuse protection, monitoring, signal protection) — each only where it makes sense for the interface type.

02

Security Properties

  • The Security section of processes and multiprocesses is split into sub-tabs — Login & accounts, Authorization, Communication, Robustness, Sessions & traceability, Operation, Data — the categories EN 303 645, EN 18031 and IEC 62443-4-2 share; each tab names its open fields
  • Each field appears only where the settings before it make it meaningful; a multiprocess's safety fields stay below the tabs, always in view
  • Secure channels instead of "TLS termination": an endpoint names every channel it offers — TLS (server), mutual TLS, VPN / IPsec, SSH, application level (e.g. OPC UA Secure Channel), other
  • Each flow's encryption in transit is checked against its endpoints — TLS / mTLS as before, SSH needs one endpoint offering it, application level both
  • The DFD findings list a channel an element offers that none of its flows uses (an open service without a visible purpose) and an element with a flow over a network or fieldbus but no channel chosen — unset is unknown, None is a choice; on-board chip buses are not asked
  • Update package encrypted (no / per device type / per device) and key / certificate renewal (not possible · encrypted update · secure channel · on site · unencrypted) as fields; the DFD warns about keys renewed in plain, over a channel the element does not offer, or in an update that is not encrypted
  • Exposed to Internet is context, not a control — it sits in the element's context, on processes as on multiprocesses
  • Black-box multiprocess: a multiprocess without a child page — a PLC drawn as a box, a supplier's module — gets seven Inside fields for the processes and data it contains, in the tab of their topic
03

Leveled DFDs

A large system rarely fits on one diagram. A project can hold several draw.io pages: a Top page and a child page for every multiprocess you decompose. It stays one model — one element namespace, one asset register, one threat and risk register.

Pages

Decompose a multiprocess

A new multiprocess can get its own child page; deleting the multiprocess removes the page. Page info sits on draw.io's page tabs, a button opens the child page.

Identity

One element, many pages

An element is defined once and appears elsewhere as a context copy. Numbers are hierarchical — P-2.1 lies under MP-2 — and a page can be renumbered with its child pages.

Context

Insert and sync context

"Insert as context" places existing elements on a child page; "Sync context" keeps the copies in line with the parent page.

Analysis

Analysed on the leaves

Threats are generated for the parts, not the decomposed multiprocess. A flow drawn on a parent level is resolved to the part that handles it; refines links keep parent and child flows balanced.

  • Incomplete decomposition never blocks work: a flow that cannot be resolved is analysed conservatively on the parent level and listed as such — nothing is dropped silently
  • The DFD validation reports leveled findings: dangling references, unbalanced flows, duplicated definitions, assets not yet assigned to a part
  • An existing multi-page draw.io file is taken over in the adoption dialog, pasted copies are assigned there too
  • One thumbnail per page; previews and the asset graph filter by page
  • A classic single-page DFD works as before
  • The shape libraries have a straight data flow; id labels widen to their id
04

Three Views of One Model

Diagram

Draw

The draw.io diagram with the side panel for the selected element and the asset panel.

Description

Describe

One accordion per element with the same forms — for working through a model element by element. Create an asset by name and category right there and link it to elements later.

Asset graph

Relate

The assets and their relations across layers; details and editing in cards on the canvas.

Each view has exactly one place to edit, and notifications open the finding in the current view.

05

Asset Graph

  • Layer view: one lane per vertical layer (data → function → system → infrastructure), process, service, physical, human and environment in a side column; presets such as Architecture, Flow or Protection targets
  • Links to hidden layers appear as counters on the node — a click shows the layer
  • Focus view around one asset or hazard (depth 1–3), including the DFD elements that relate to it — they can be switched off in the focus view too
  • Hazard items as read-only nodes in their own lane above the protection targets, coloured by their worst severity, with contributes_to and endangers edges (severity as label); a card with causes and targets and "Open in Hazard tab"; on with the presets All and Protection targets — only hazards marked relevant (in scope) are shown
  • Relation type filter and search; a hit in a hidden layer or outside the focus says why and offers to show it
  • A relation filter (DFD element, asset and hazard relations) shows what is still to be linked
  • Cards for assets (relations grouped by type) and links (type, step, rationale, degraded mode); "Show in graph" from the asset table and "Show in table" back
  • Mouse as in draw.io: drag a node to move it, Ctrl / ⌘ + drag pans the view, the wheel zooms. Nodes of the data … infrastructure lanes move along their lane; side-column nodes snap to a row, including two free rows above the top lane
  • Three rows per category lane (and in the free rows) to align assets; Rearrange spreads a crowded category over its rows by the assets' links, so fewer lines cross
  • Stable layout: nodes move only when you drag them or on "Rearrange"; positions are remembered locally per project, never in the project file
  • Leveled DFDs: filter by page; a decomposed multiprocess shows the assets of its parts as a read-only roll-up ("via P-2.1, DS-2.1")
  • Keyboard: Tab and arrow keys select, Enter focuses, Delete removes (edit mode), Esc closes
06

Modeling in the Asset Graph

  • Edit mode is visibly marked; view mode is the default
  • Connect two assets by dragging from a node's handle — while dragging, every asset is marked as valid, valid only the other way round, or not allowed; the chooser offers only the allowed types, core types first
  • Relate a DFD element to an asset from the element's handle or with "Link to element" in the asset card — only the relation types the element rules allow
  • Create an asset in a layer, delete one with a confirmation that lists everything depending on it
  • Edit link attributes and asset properties in the card — the same forms and the same write path as the side panel
  • Undo / redo for link changes
07

DFD Completeness Rules

  • All system components, data flows, and trust boundaries must be present
  • All elements must be named and numbered (P-xx, MP-xx, DS-xx, DF-xx, EE-xx, SE-xx, AC-xx; on child pages hierarchically, e.g. P-2.1)
  • Assets and Interfaces must be placed on the correct elements
  • Consistent with architecture — version-controlled in repository
  • Re-assessment trigger when context or architecture changes
