DFD Modeling

TARAflow uses draw.io as its DFD editor. Import or draw your data-flow diagram, then parametrize each element with type, technology, protocol, and security properties.

01

Element Types

Process [P-xx]

Process

Software component, service, or controller. Properties: technology (bootloader, rtos_task, driver, protocol_stack), malwareProtection, accountManagement.

DataStore [DS-xx]

DataStore

Persistent storage. Properties: technology (flash, eeprom, ram, database), encryption, backupMechanism.

DataFlow [DF-xx]

DataFlow

Communication channel. Properties: protocol, encryptionInTransit, location (field_cable, on_board), safetyFunction, accessMode.

ExternalEntity [EE-xx]

ExternalEntity

Actor outside the system boundary. Properties: entityType (human, external_system, sensor).

TrustBoundary [TB-xx]

TrustBoundary

Logical security zone boundary. Threats are generated at crossing points.

PhysicalBoundary [PB-xx]

PhysicalBoundary

Physical enclosure boundary. Properties: tamperProtection, physicalAccessControl, physicalMobility.

ChipBoundary [CB-xx]

ChipBoundary

Hardware security boundary. Properties: chipType, debugInterfaceLocked, sideChannelProtection, cryptoStandard.

Interface [IF-xx]

Interface / PhysicalInterface

Physical or logical interface port. Properties: implementedControls (logicalAccessControl, debugProtection, physicalAccessProtection, abuseProtection, monitoringControl).

02

Leveled DFDs

A large system rarely fits on one diagram. A project can hold several draw.io pages: a Top page and a child page for every multiprocess you decompose. It stays one model — one element namespace, one asset register, one threat and risk register.

Pages

Decompose a multiprocess

A new multiprocess can get its own child page; deleting the multiprocess removes the page. Page info sits on draw.io's page tabs, a button opens the child page.

Identity

One element, many pages

An element is defined once and appears elsewhere as a context copy. Numbers are hierarchical — P-2.1 lies under MP-2 — and a page can be renumbered with its child pages.

Context

Insert and sync context

"Insert as context" places existing elements on a child page; "Sync context" keeps the copies in line with the parent page.

Analysis

Analysed on the leaves

Threats are generated for the parts, not the decomposed multiprocess. A flow drawn on a parent level is resolved to the part that handles it; refines links keep parent and child flows balanced.

  • Incomplete decomposition never blocks work: a flow that cannot be resolved is analysed conservatively on the parent level and listed as such — nothing is dropped silently
  • The DFD validation reports leveled findings: dangling references, unbalanced flows, duplicated definitions, assets not yet assigned to a part
  • An existing multi-page draw.io file is taken over in the adoption dialog, pasted copies are assigned there too
  • One thumbnail per page; previews and the asset graph filter by page
  • A classic single-page DFD works as before
03

Three Views of One Model

Diagram

Draw

The draw.io diagram with the side panel for the selected element and the asset panel.

Description

Describe

One accordion per element with the same forms — for working through a model element by element.

Asset graph

Relate

The assets and their relations across layers; details and editing in cards on the canvas.

Each view has exactly one place to edit, and notifications open the finding in the current view.

04

Asset Graph

  • Layer view: one lane per vertical layer (data → function → system → infrastructure), process, service, physical, human and environment in a side column; presets such as Architecture, Flow or Protection targets
  • Links to hidden layers appear as counters on the node — a click shows the layer
  • Focus view around one asset (depth 1–3), including the DFD elements that relate to it
  • Relation type filter and search; a hit in a hidden layer or outside the focus says why and offers to show it
  • Cards for assets (relations grouped by type) and links (type, step, rationale, degraded mode); "Show in graph" from the asset table and "Show in table" back
  • Stable layout: nodes move only on "Rearrange"; positions are remembered locally per project, never in the project file
  • Leveled DFDs: filter by page; a decomposed multiprocess shows the assets of its parts as a read-only roll-up ("via P-2.1, DS-2.1")
  • Keyboard: Tab and arrow keys select, Enter focuses, Delete removes (edit mode), Esc closes
05

Modeling in the Asset Graph

  • Edit mode is visibly marked; view mode is the default
  • Connect two assets by dragging from a node's handle — while dragging, every asset is marked as valid, valid only the other way round, or not allowed; the chooser offers only the allowed types, core types first
  • Relate a DFD element to an asset from the element's handle or with "Link to element" in the asset card — only the relation types the element rules allow
  • Create an asset in a layer, delete one with a confirmation that lists everything depending on it
  • Edit link attributes and asset properties in the card — the same forms and the same write path as the side panel
  • Undo / redo for link changes
06

DFD Completeness Rules

  • All system components, data flows, and trust boundaries must be present
  • All elements must be named and numbered (P-xx, DS-xx, DF-xx, EE-xx; on child pages hierarchically, e.g. P-2.1)
  • Assets and Interfaces must be placed on the correct elements
  • Consistent with architecture — version-controlled in repository
  • Re-assessment trigger when context or architecture changes
