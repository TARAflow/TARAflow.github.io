Audit Trail

The project's history lives in git: path-scoped, signed commits per assessment round, a signer manifest that says who may sign, and the Audit Verification Engine that checks the whole trail — in the app, in git hooks and in CI.

01

Commits per Round

  • The audit repository is found from the project file's location — the repository root may be a parent folder, several projects can share one repository
  • The commit dialog shows the changes phase by phase, lets you pick the branch and the round — Initial Assessment, Detail Review, Refinement, Final Decision, Verification or your own — and can push
  • A commit stages only the project's own files; its message is [TARA] <round> with the trailers Affected-Phases, Batch-Size, Author and Date; changes to the signer manifest are audit: commits
  • The project file is written in one canonical form, so a save without a change leaves git clean and every diff shows only what changed
  • The audit configuration (General, Authentication, Rounds, Signing, Protection) is pre-filled from the repository's git config — remote, author, signing key
02

DFD Diff

  • The commit dialog lists DFD changes per element and flow, classified as semantic, graphical, structural or identity change
  • Leveled DFDs: changes per page, definition, context copy and layout
  • The analysis effect is shown — e.g. a flow that is now resolved below a multiprocess instead of on the parent level
  • Scrolling the canvas or an undone edit is not recorded as a change
03

TARA Verification

  • ISO/SAE 21434 projects: record the verification of the TARA — the four points of RQ-09-07 as a checklist, result and findings
  • Sealed with a hash of the analysis: TARAflow tells you when the analysis changed since, or when the verification is older than 90 days
  • Ticket and status changes of mitigations do not count as a change of the analysis
  • The status shows in the Overview, the phase bar and the report
04

Signing & Identity

  • Once an audit repository has a signer manifest, every commit in it is signed, for every project
  • The commit dialog tells you before the click when a key or an authorization is missing
  • A commit checks out the audit branch before staging; a save after a project switch lands in the right project
  • Signing with SSH (default) or GPG, with a dedicated signing key; the signer manifest .tara/allowed_signers lists who may sign and who is a maintainer — only maintainers may change it
  • A signed commit is refused when the author's e-mail is not in the manifest
  • The commit author stays on your machine — it is not written into the project file, every team member uses their own
05

Audit Verification Engine

  • Walks the history from the audit anchor — the first commit that adds the signer manifest, pinned by its hash — to the tip
  • Every commit must be signed by a signer the manifest allowed before that commit; a manifest change must be signed by a maintainer
  • Further checks: linear history, clean working tree, the audit-root tag, the commit message schema, the canonical form of every changed project file, optionally four eyes (Reviewed-by)
  • Findings with stable rule codes and severities; the same engine runs in the Audit tab and as the command-line tool taraflow-verify for CI, where the anchor is pinned in a policy
  • A managed commit-msg git hook checks the message schema — for commits made on the console too
  • The Protection checklist guides the server side: protected branch, signed and linear history, CODEOWNERS for .tara/
