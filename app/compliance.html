App / 09

Compliance

The requirement matrices of your component — IEC 62443-4-2 in the classic edition (2019) or the CRA edition EN IEC 62443-4-2, and EN 50742 Approach A — derived from the DFD, the risk treatment and the project data you already have. Rows are checked, not ticked.

01

Choosing the Matrix

  • The tag decides: IEC 62443 for the classic edition with its device categories, EN IEC 62443 (CRA) for the CRA edition (draft prAA:2026, marked as draft)
  • With both tags the two editions appear side by side as sub-tabs; the EN 50742 A tag adds a sub-tab of its own
  • One statement per requirement holds in both editions — switching between the classic and the CRA tag keeps your statements
02

Security Levels

SL-T

Target

Choose the component (or the whole model) and set the target security level per foundational requirement.

SL-C

Achieved

What the product reaches from the model and the mitigations marked done.

SL-C planned

Planned

What it reaches once the chosen mitigations are done.

With system

With measures of the system

The value including the supporting measures of the system around the component.

03

Derived, Not Ticked

  • Every row is checked against the DFD properties, the mitigations of the risk treatment (per element; only done ones count for the achieved value) and supporting measures
  • An unset property is information missing, never not applicable — the row names the empty field per element, e.g. "information missing on MP-1 (password lifetime limit)"
  • A row met by a statement while the model is still open says so; rows an edition declares void link to a dialog with the reason
  • A requirement the plant provides is covered by a supporting claim — it counts for the value with measures of the system, never for the product's SL-C; claims no requirement uses any more can be deleted
  • Project mitigations say which IEC 62443-4-2 requirements they implement
  • What the model cannot show gets a statement with reasoning and evidence; TARAflow tells you when the model changed since
  • Hover a requirement number for its title and summary, click it for everything — how TARAflow checks it, the elements concerned, fitting catalog mitigations, your statement. The summaries are in our own words; the standard is authoritative
04

What to Do Next

  • A to-do list up to the SL-T names, per element, the property to set or check, marks what the planned mitigations close and lists the missing statements
  • A click on the element shows it in the diagram; a filter shows the rows by status
  • A quick guide walks through the steps
  • The report gets a chapter with one part per active standard: the security levels, the statement of applicability (with the source of every row), the CRA view by Annex I letter and the gaps against the SL-T with the text of the suggested catalog mitigations — in every format and the CLI

Example: the Pump Station Controller in TARAflow_Examples is an IEC 62443 / CRA example project to try the matrix on.

05

Model Fields for the Matrix

  • Processes, multiprocesses and data flows carry the fields the requirements ask about: user accounts (per person / per role / shared), password rules and lifetime, role-to-permission mapping, default credentials, login lockout, update delivery and defaults, secure by default, deletion of user data, access mode and data minimisation
  • Each field appears only where the settings before it make it meaningful; more IEC 62443-4-2 rows are derived instead of needing a statement (CR 1.1 RE(1), CR 1.5, CR 1.7, CR 1.11, CR 2.1 RE(2), CR 3.10, CR 7.6, CR 7.9)
  • Filter Information missing to see which field each row still waits for
06

EN 50742 Approach A

  • With the EN 50742 A tag the Compliance tab shows the 23 baseline requirements next to the IEC 62443 editions
  • Checked against the model, the risks (SRSL, mandated §7.4.3 controls) and the project data — hazards, safety functions, window of opportunity, system definition
  • The header shows the highest SRSL per safety function and the interfaces on the path to it, derived from the DFD; a one-way boundary (data diode) ends the path
  • The report has its own part in the requirement matrix chapter
