Threat Modeling Process

The TARAflow
Methodology

A structured, graph-based TARA process covering system decomposition, asset definition, threat generation, risk assessment, and governance — traceable from DFD element to implemented control.

01

Process Flow

Phase 0
Artefact → Project & Context Profile

Project Initialization

  • Project name, version, responsible roles
  • System description and scope
  • Rating mode: ISO 21434 (feasibility-only) or Standard/IEC 62443 (feasibility × motivation)
  • Safety-relevant toggle — enables Phase 1 (Hazard Identification) when on
  • Industry, platform, and regulatory tags
Phase 1
Artefact → Hazard / Bowtie Register (optional)

Hazard Identification

  • Only present when the project is marked safety-relevant
  • Model each hazard as a Bowtie: contributing causes → hazard (with AND/OR gate) → endangered safety goals
  • Triage every hazard: reachable by a cyberattack (in scope), not cyber-caused (out of scope), or unknown
  • In-scope hazards feed the Safety Annotation Layer used in Asset and Risk impact
Phase 2
Artefact → Validated DFD

DFD Modeling

  • Architecture overview and system scope
  • Create DFD with all elements (Process, DataStore, DataFlow, ExternalEntity)
  • Define Trust Boundaries, PhysicalBoundaries, ChipBoundaries
  • Identify and place Interfaces (IF-xx, physical and logical)
  • Describe all DFD elements with type, technology, protocol properties
  • Mark assets on DFD elements
Phase 3
Artefact → Asset Table

Asset Definition

  • Inventory assets across all element groups
  • Assess criticality: business and physical impact
  • Assign CIANAAA protection goals per asset
  • Asset-to-security-goal mapping drives threat generation
Phase 4
Artefact → Threat Table

Threat Analysis

  • STRIDE per element and per interaction
  • Context-aware template matching
  • Threat table with assets, mitigations, verifications
  • Prioritize by asset impact
Phase 5
Artefact → Attack Trees, Path Feasibility

Attack Tree

  • A third threat generator alongside per-element and per-interaction STRIDE — always this phase, in this position, in both rating modes
  • Refine an existing STRIDE threat's feasibility, or model a new attack path STRIDE has no element for (supply chain, physical access, social engineering)
  • Feasibility per attack-potential factors (elapsed time, expertise, knowledge, window of opportunity, equipment)
  • Gate aggregation follows the quantity being composed — sum/min for effort, product/union for probability
// ISO 21434 mode

Feasibility is the likelihood axis

  • Phase 5 is used comprehensively — it is where Cl. 15.6/15.7 attack feasibility is normatively determined
  • Attacker motivation is excluded from the risk number (Cl. 3.1.29): unattributable, and it would become a licence to argue a risk away
  • An audit-grade RC-15-11 method is required on every rated leaf
// Standard / IEC 62443 mode

Feasibility × motivation

  • Phase 5 is used opportunistically — on coverage gaps STRIDE can't reach, and on threats whose exploitability is uncertain
  • Attacker benefit counts toward likelihood alongside feasibility, as threat-actor profiles do
  • Quick, unrated-effort estimates are permitted alongside the audit-grade method
// Same phase, different role

The rating mode changes how Phase 5's output is used — and, in Standard mode, how thoroughly it's applied — never whether it happens or where it sits. The Attack Tree always follows Threat Analysis and always precedes Risk Assessment.

Phase 6
Artefact → Risk Register, Risk Matrix

Risk Assessment

  • One register — STRIDE-derived and attack-path-derived threats are both just threats here
  • Risk = Impact × Likelihood, impact anchored to (Asset × Security Goal)
  • MoSCoW prioritization of mitigations
  • Risk before and after mitigation tracked
Phase 7
Artefact → CBA, Sign-off, Audit Trail

Validation & Governance

  • Cost-benefit analysis for "Won't fix" decisions
  • Attack-tree validation of Won't decisions
  • Risk owner sign-off
  • Re-assessment trigger definition
Re-assess
Triggers

Re-Assessment Cycle

  • Architecture changes
  • New threats or CVEs
  • Regulatory changes
  • Annual review
02

Core Concepts

Graph-based Model

Every element in TARAflow is a node: assets, DFD elements, threats, mitigations, and verifications are all first-class entities with typed edges between them. This enables full traceability in both directions — from asset to mitigation and back.

STRIDE per Element & Interaction

Threats are generated from two complementary perspectives: per DFD element (internal vulnerabilities) and per interaction (communication and channel risks). Context-aware template matching filters templates by element type, technology, protocol, and system class.

S — Spoofing T — Tampering R — Repudiation I — Info Disclosure D — Denial of Service E — Elevation

CIANAAA Protection Goals

TARAflow extends the classic CIA triad to CIANAAA: Confidentiality, Integrity, Availability, Non-repudiation, Authenticity, Authorization, and Auditability. Each asset's active protection goals drive which STRIDE categories are generated — assets without a goal produce no threats.

Closed-Loop Mitigation

When a DFD element property indicates an implemented control — for example implementedControls.logicalAccessControl = mfa — TARAflow automatically marks the corresponding mitigation as already implemented. The threat is still generated (nothing is suppressed), but the mitigation is pre-filled and flagged, enabling before/after risk comparison.

Safety Annotation Layer

Relationships between assets carry safety annotations: relevance (direct / indirect) and impact (reversible / irreversible / fatal). A safety override rule automatically escalates threats to CRITICAL when the combination of direct relevance and fatal impact is present — independent of CIANAAA scoring.

Architecture-Centric, Bottom-Up

TARAflow follows a bottom-up principle: the DFD defines the system, and all analysis flows from it. Threat generation is always driven by the model — not by freeform text entry. This keeps the assessment consistent with the actual architecture and makes re-assessment tractable when the system changes.

03

Standards Alignment

IEC 62443

Industrial Automation & Control Systems

Security levels, zones and conduits, CIANAAA goals, and countermeasure requirements (CR) map directly to TARAflow's asset model and mitigation catalog.

ISO/SAE 21434

Automotive Cybersecurity

TARA as mandatory activity, asset identification, threat scenario and risk value determination — all covered by the Phase 0–7 workflow.

EU Cyber Resilience Act

Connected Products

Vulnerability handling, secure-by-default, and lifecycle documentation requirements map to TARAflow's audit trail, re-assessment cycle, and mitigation tracking.

EN 50742 / Maschinenverordnung

Machinery & Safety

Safety-security integration: the Safety Annotation Layer captures physical hazard potential in alignment with ISO 12100 risk estimation concepts.

OWASP Risk Rating

Likelihood Factors

Threat likelihood is scored using OWASP Risk Rating factors (skill level, motive, opportunity, size of threat agent group, ease of exploit, intrusion detection).

ETSI TVRA / ISO 27005

Threat & Vulnerability Analysis

The TARA process structure is compatible with ETSI Threat Vulnerability Risk Analysis and ISO 27005 information security risk management.
